# Описание контейнерной архитектуры (TO-BE Container Diagram)

## 1. Таблица ответственности компонентов и контейнеров

| Контейнер / Система | Тип | Звено / Технология | Зона ответственности и выполняемая роль |
| :--- | :--- | :--- | :--- |
| **Клиент / Сотрудник** | Person | — | Внешние роли. Клиент инициирует платеж, Сотрудник (25 человек) выносит финальный вердикт по аномалиям. |
| **API Gateway** | Container | Единая точка входа | Принимает внешние запросы, осуществляет первичную авторизацию и маршрутизирует трафик во внутренние сервисы ABS. |
| **Incoming payments** | Container | Backend (Java/Go) | Сервис первичного приема платежей. Проводит базовый форматно-логический контроль (ФЛК) формы документа и регистрирует операцию. |
| **Шина данных (Kafka)** | Container | Message Broker | Единая событийно-ориентированная шина (Event Bus). Хранит топики входящих, обработанных платежей и вердиктов сотрудников, обеспечивая историчность и отказоустойчивость конвейера. |
| **Model connector** | Container | Backend (Java/Go) | Оркестратор антифрод-контура. Читает пачки транзакций из Кафки, обогащает их контекстом скользящего окна из БД, вызывает ИИ-модель по gRPC и пушит результаты обратно в шину. |
| **Antifrod model** | Container | ML Service (Python) | Локальное вычислительное ядро ИИ (On-Premise). Содержит ансамбль моделей (RuBERT + Isolation Forest), рассчитывает индекс аномальности от 0 до 1. |
| **Kafka DB Connect** | Container | Kafka Connect | Асинхронный консьюмер. Разгружает операционную базу, переливая статусы и вердикты из очередей Кафки в реляционные таблицы в фоновом режиме. |
| **Операционная БД** | Container | СУБД (PostgreSQL) | Аналитическое хранилище данных. Хранит историю клиентов, агрегаты активности и лог ручных вердиктов. Изолирована от прямого транзакционного шлюза. |
| **Employee tools** | Container | Frontend / CRM | Рабочее место операторов финмониторинга. Выводит ТОП-20 аномальных операций за такт из БД и отправляет ручные вердикты сотрудников в Кафку. |
| **Outcoming payments** | Container | Backend (Java/Go) | Исполнительный сервис исходящего шлюза. Слушает топик обработанных платежей Кафки, мгновенно отправляет чистые транзакции (Cleared) во внешний шлюз и игнорирует замороженные (Suspended). |
| **Платежный шлюз** | External System| Legacy Software | Внешняя расчетная система банка, осуществляющая физическую отправку денег контрагентам. |

## 2. Архитектурное обоснование состава звеньев ИИ-конвейера

Состав технологических звеньев для каждой инициативы подобран строго под физику бизнес-задачи. Все избыточные элементы (ИИ-промпты, генеративные LLM-модели, RAG-контуры текстового поиска) умышленно исключены из архитектуры для минимизации галлюцинаций и снижения стоимости вычислительной инфраструктуры (TCO):

1. **Для Инициативы №1 (Финмониторинг):** Реализован классический таблично-семантический конвейер аномалий (*Признаки скользящего окна → Модель Isolation Forest → Сортировка пачки → Детерминированный роуминг*). Контур Retrieval отсутствует, так как транзакционный поток полностью автономен и не требует внешних текстовых баз знаний.
2. **Для Инициативы №2 (Распознавание сканов):** Применен конвейер извлечения и валидации (*Графическая детекция букв → NER-сегментация именованных сущностей → Детерминированный ФЛК на бэкенде*). Звено NER необходимо для перевода неструктурированного текста в жесткую JSON-структуру CRM-системы.
3. **Для Инициативы №10 (Антифрод документов):** Спроектирован гибридный двухконтурный конвейер. В логический контур конвейера **явно включено звено Retrieval (Инструмент внешнего запроса)** — детерминированный gRPC-коннектор к API ФНС / ГИР БО. Данное звено необходимо как объективный внешний контекст для валидации извлеченных из отчетности цифр. Также для И10 зафиксировано обязательное **звено Дообучения (Active Learning)** на проде для адаптации моделей к меняющимся пиксельным паттернам подделок мошенников.
